# Git and release strategy

How EduBridge moves code from a laptop to staging to production without polluting `main`, and how every commit stays consistent — including commits generated by Cursor.

**Cursor always-on rule:** `.cursor/rules/50-git-workflow.mdc`  
**Agent skill:** `.agents/skills/edubridge-git/SKILL.md`  
**Commit voice:** `.agents/skills/caveman-commit/SKILL.md` (Conventional Commits, terse)

## Branch model

```text
feature/<short-name>  ──PR──►  development  ──PR──►  main
                                  │                    │
                                  ▼                    ▼
                             staging / test         production
```

| Branch | Purpose | Who deploys from it |
|--------|---------|---------------------|
| `main` | Always production-ready | Coolify + Hetzner (`*.edubridge.app`) |
| `development` | Integration branch | Vercel staging (`*.dev.edubridge.app`) |
| `feature/<short-name>` | One concern, short-lived | Optional PR preview URLs |
| `hotfix/<short-name>` | Urgent fix branched from `main` | Production, then sync to `development` |

**Rules:**

- Do not use `master`.
- Do not push feature work directly to `main`.
- Do not keep long-lived personal branches.
- Protect `main` and `development` on GitHub (PR required, CI green) once more than one person commits.
- CI/CD lives in `.github/workflows/ci-cd.yml`. `verify` runs on PRs/pushes to `development` and `main`. Image publish, smoke, and Coolify deploy run only on `main`. Vercel deploys `development` through Git integration. Never put `pnpm db:migrate` in CI. Never set `NODE_ENV` in platform env vars.

### Naming examples

- `feature/phase-0-auth`
- `feature/shell-module-registry`
- `fix/report-card-pdf-margin`
- `hotfix/session-cookie-secure`

## Day-to-day workflow

1. Update integration: `git checkout development && git pull`
2. Branch: `git checkout -b feature/<short-name>`
3. Implement; keep commits small and conventional (below)
4. Push and open **PR → `development`** (squash merge preferred)
5. Verify on **Vercel staging** under `*.dev.edubridge.app`
6. When ready for users: open **PR `development` → `main`**, merge, deploy production

### Hotfix

1. `git checkout main && git pull`
2. `git checkout -b hotfix/<short-name>`
3. Fix → PR → `main` → deploy
4. Merge or cherry-pick into `development` so staging does not drift

### First commit / empty repo bootstrap

If the repo has no commits yet:

1. Make the initial commit on `development` (scaffold only — no feature branch required)
2. `git branch main` at the same commit
3. Push `main` and `development`
4. Set GitHub default branch to `main`
5. Wire production → `main`, staging → `development`
6. After that, always use feature branches

## Commit message standard

Every commit — human or Cursor-generated — uses **Conventional Commits**:

```text
<type>(<scope>): <imperative summary>

[optional body]
```

| Piece | Convention |
|-------|------------|
| Type | `feat` `fix` `refactor` `perf` `docs` `test` `chore` `build` `ci` `style` `revert` |
| Scope | Prefer: `web` `agent` `docs` `ui` `ai-ui` `db` `auth` `shell` `student-dashboard` `report-cards` `test-papers` `repo` `ci` |
| Subject | Imperative (“add”, not “added”); ≤72 chars; no trailing period |
| Body | Only for non-obvious *why*, breaking changes, migrations, `Closes #N` |

**Do not** put AI marketing footers, emoji, or “This commit does…” in messages.

**Breaking change:**

```text
feat(api)!: rename entitlement field

BREAKING CHANGE: module_flags renamed to module_entitlements.
```

### Examples

```text
feat(auth): add school-scoped session claims
fix(shell): keep module pill in sync with route
chore(repo): ignore agent scratch and runtime logs
docs(guides): document git and release strategy
```

## What never gets committed

Ignored by root `.gitignore` (do not force-add):

- `node_modules`, `.pnpm-store*`, `.turbo`, `.next`, `dist`
- `.env`, `.env.*` (except `*.env.example`)
- `*.log`, `.wayfinder/`, `.scratch/`, `.mastra/`, `*.db`, secrets (`*.pem`, `*.key`)

**Do commit** shared agent config: `.agents/`, `.cursor/rules/`, `AGENTS.md`, `skills-lock.json`.

## Pull requests

| Direction | Merge style | Gate |
|-----------|-------------|------|
| Feature → `development` | Squash and merge | CI: `pnpm lint`, `pnpm check-types`, `pnpm build` |
| `development` → `main` | Prefer one clear release merge | Staging signed off |
| Hotfix → `main` | Squash | CI green + sync to `development` |

PR title should match the intended squash commit subject. Include a short test plan in the body.

## Changelog and in-app “What’s new”

| Layer | Where | Audience |
|-------|-------|----------|
| Engineering changelog | Root `CHANGELOG.md` ([Keep a Changelog](https://keepachangelog.com/)) | Developers |
| GitHub Releases | Tag / release from `main` | Developers / ops |
| In-app updates | Product copy / CMS later | School admins & teachers |

Keep `[Unreleased]` in `CHANGELOG.md` while work lands on `development`. When cutting a production release from `main`, move bullets into a dated version section.  
**Never** paste raw `feat(scope): …` lines into the school-facing UI.

## Rollback

1. Prefer `git revert` of the merge commit on `main` (safe, auditable) over hard resets.
2. Coolify: pin the previous GHCR tag (`sha-<commit>`). Do not rebuild on the VPS.
3. Sync `development` so staging matches (merge or revert the same change there).
4. Fix forward on a new `feature/*` or `hotfix/*` branch.

Avoid `git push --force` on `main` or `development`.

## Checklist for agents (Cursor)

When the user asks to commit or open a PR:

- [ ] On the correct branch (`feature/*` / `hotfix/*`, not dirty work on `main`)
- [ ] No secrets or ignored junk staged
- [ ] Message follows Conventional Commits + caveman-commit terseness
- [ ] User explicitly asked to commit / push / open PR
- [ ] After merge to `development`, remind about staging verification before `main`
